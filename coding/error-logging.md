# 에러 처리·로깅 규칙

> 상태: 확정 (2026-07-11)
> API 에러 응답 형식은 `rest-api.md`를 따른다.

## 에러 전파: 예외 기본

- **실패는 예외를 던져 전파한다.** 언어 기본 방식이라 마찰이 없고,
  호출 스택 어디서든 잡을 수 있다.
- 예외가 아닌 것: **"없음이 정상"인 경우**는 예외 대신 null을 반환한다.
  `find`류 함수가 여기에 해당한다 (naming.md 표준 동사와 연결 —
  `get`은 없으면 예외, `find`는 없으면 null).

## 예외 계층

- 도메인 예외의 공통 부모(`AppError` 등)를 하나 두고, 그 아래에
  구체 예외를 만든다.
- **도메인 예외는 응답에 필요한 정보를 스스로 갖는다** — HTTP 상태,
  응답 code(rest-api.md의 숫자 코드), 개발자용 message. 경계 핸들러는
  이 정보를 읽어 envelope로 변환만 한다.

```python
class OrderNotFoundError(AppError):
    http_status = 404
    code = 404001
```

## 어디서 잡는가: 경계에서만

- **예외는 진입 경계의 공통 핸들러에서 잡는다** — API 예외 핸들러,
  메시지 컨슈머, 배치 잡의 최상위. 거기서 로그를 남기고 에러 응답으로
  변환한다.
- 중간 계층은 **복구할 수 있을 때만** catch한다 (재시도, 대체값, 보상
  트랜잭션). 복구하지 못할 예외는 잡지 않고 통과시킨다.
- **삼키기 금지.** 빈 catch, 로그만 찍고 계속 진행하는 catch는 쓰지
  않는다. 잡았으면 복구하거나, 못 하면 다시 던진다.

## 로그 포맷: 구조화(JSON)

- 로그는 **필드 기반 JSON 한 줄**로 남긴다. 수집·검색 도구에서 필드로
  쿼리하기 위함. 로컬 개발 중에만 사람용 포맷으로 출력한다.
- 메시지에 값을 문자열로 섞지 않고 필드로 분리한다.
  - `logger.info("주문 생성", order_id=42, user_id=7)` (O)
  - `logger.info(f"주문 42 생성됨 (user 7)")` (X — 검색 불가)
- 요청 단위 추적을 위해 **요청 ID(request_id)를 모든 로그에 포함**한다.
- **민감정보(비밀번호, 토큰, 개인정보)는 로그에 남기지 않는다.**

## 로그 레벨

| 레벨 | 기준 |
| --- | --- |
| `ERROR` | **사람의 조치가 필요한 예상 밖 실패만.** 울리면 무조건 봐야 하는 레벨로 유지한다 |
| `WARN` | 비정상이지만 동작에 지장 없음 (재시도 성공, 폴백 사용, 사용자 입력 오류·404 등 정상적 실패) |
| `INFO` | 주요 이벤트 (요청 처리, 주문 생성, 배치 시작·종료) |
| `DEBUG` | 개발·진단용 상세. 운영 기본 레벨은 INFO |

- 판단 기준은 하나다: **"이 로그가 울리면 내가 지금 확인할 것인가?"**
  아니라면 ERROR가 아니다. 4xx는 원칙적으로 WARN 이하, 5xx는 ERROR.
