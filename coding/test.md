# 테스트 규칙

> 상태: 확정 (2026-07-11)
> 테스트 파일 이름은 `naming.md`를 따른다 — `*.test.ts` / `tests/test_*.py`

## 구조: given-when-then

- 모든 테스트는 준비(given) · 실행(when) · 검증(then) 세 블록으로 나눈다.
  테스트가 길어져도 읽는 순서가 고정된다.
- 블록 구분은 빈 줄로 하고, 흐름이 복잡할 때만 주석을 단다.

```typescript
test("재고가 없으면 주문이 실패한다", () => {
  // given
  const product = createProduct({ stock: 0 });

  // when
  const result = orderService.placeOrder(product.id, 1);

  // then
  expect(result.code).toBe("OUT_OF_STOCK");
});
```

## 이름: 한국어 문장

- **테스트 설명은 "~하면 ~한다" 형태의 한국어 문장**으로 쓴다.
  실패 로그에서 무엇이 깨졌는지 문장으로 바로 읽힌다.
  커밋 메시지 한국어 결정과 일관.
  - TypeScript: `test("재고가 없으면 주문이 실패한다", ...)`
  - Python: 함수명은 영어 요약, docstring에 한국어 문장 병기
    ```python
    def test_order_fails_when_out_of_stock():
        """재고가 없으면 주문이 실패한다."""
    ```

## 비중: 단위 중심 + 핵심 경로 통합

- **빠른 단위 테스트가 기본.** 도메인 로직·계산·분기는 단위 테스트로
  촘촘하게 덮는다. 빠르게 돌아야 자주 돌리고, 자주 돌려야 의미가 있다.
- **핵심 흐름만 통합 테스트로 보강한다.** 결제, 인증, 주문 생성처럼
  깨지면 치명적인 경로는 실제 구성요소를 연결해 end-to-end로 검증한다.

## 커버리지: 숫자를 강제하지 않는다

- 커버리지는 **참고 지표**로만 본다. 숫자를 목표로 삼으면 검증 없는
  의미 없는 테스트가 생긴다.
- 대신 행동 규칙으로 관리한다:
  - 새 기능에는 테스트를 함께 작성한다.
  - **버그를 고치면 그 버그를 재현하는 테스트를 반드시 남긴다.**
    같은 버그가 두 번 나올 수 없게 하기 위함.

## Mock: 경계에서만

- **제어할 수 없는 경계만 mock한다** — 외부 API, 시간(now), 랜덤,
  파일시스템, 네트워크.
- **내 코드끼리는 실제 객체를 쓴다.** 내부 협력 객체까지 mock하면
  테스트가 구현 세부에 결합되어, 동작이 같아도 리팩토링만 하면 깨지는
  테스트가 된다.
- 시간·랜덤은 주입 가능하게 설계한다 (`Clock` 주입 등). mock이 어렵다면
  설계가 경계를 안 나눈 신호다.
