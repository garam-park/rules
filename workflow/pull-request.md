# PR·리뷰 규칙

> 상태: 확정 (2026-07-11)
> 브랜치·머지 방식은 `git/branch.md`를 따른다.

## 모든 머지는 PR을 거친다

- 혼자 작업해도 develop·main으로의 머지는 **항상 PR 경유**.
  - 셀프 리뷰 기회가 강제로 생긴다.
  - CI가 머지 전에 돈다.
  - 작업 단위의 기록(제목, 설명, diff)이 남는다.
- PR 제목은 커밋 메시지 규칙(Conventional Commits)과 같은 형식으로 쓴다.

## PR 크기: 리뷰 용량 기준

- AI가 코드를 생성하는 시대에는 줄 수 제한이 의미가 없다 — 작성 비용은
  급감했고, 병목은 **사람의 리뷰 용량**이다. 크기 기준도 거기에 맞춘다.
- **기준: 한 번의 셀프 리뷰 세션에서 전부 이해하고 검증할 수 있는 단위.**
  읽다가 "이 부분은 대충 봐도 되겠지"가 나오면 그 PR은 너무 크다.
- 리뷰가 필요 없는 변경과 판단이 필요한 변경을 섞지 않는다:
  - **기계적 변경(rename, 포맷팅, 이동)은 별도 PR로 분리**한다.
    사람이 판단해야 할 diff를 최소로 유지하기 위함.
  - 리팩토링과 기능 변경도 한 PR에 섞지 않는다.
- 하나의 PR은 하나의 목적만 갖는다.

## 머지 조건

1. **CI 통과** — 테스트·린트를 기계가 강제한다.
2. **셀프 리뷰** — diff를 처음부터 끝까지 다시 읽고 머지한다.
   작성 직후보다 하루 묵혔다 보는 것이 효과적이다.
   - AI가 생성한 코드는 특히: 이해하지 못한 줄은 머지하지 않는다.
